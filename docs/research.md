# 领域调研与设计取舍

> 目的：说明“为什么这样设计、为什么不引现成库”以及关键取舍依据。

## 1. 主流方案盘点

| 方案 | 定位 | 依赖 | 与底座契合度 |
| --- | --- | --- | --- |
| go-update / selfupdate | 自更新 | 重（二进制替换库） | 不活跃、API 与 errx/logx 不一致 |
| minio/selfupdate | 二进制自更新 | 0 | 仅替换，无清单/校验/平台细节 |
| rhysd/go-github-selfupdate | GitHub 自更新 | go-github 等 | 绑定 GitHub，无自定义源/签名 |
| crate-ci/cargo-update | Rust 生态 | — | 非 Go |
| electron-updater | JS 生态 | — | 非 Go |

## 2. 自研结论

现成方案要么绑定单一发布源（GitHub），要么只解决“替换”不解决
“检查/清单/校验/回滚”，且错误语义与 errx/logx 不一致。自研成本
可控，且能：

- 源接口抽象：HTTP 清单源（自建 CDN）+ GitHub Releases 源并存；
- 安全模型统一：SHA256 必需 + Ed25519 可选 + 大小上限 + TOCTOU 防护；
- 平台差异清晰：Unix 原子替换 / Windows 启动时替换；
- 与 confx/logx/errx/jobx/webx 原生组合；
- 0 第三方依赖。

## 3. 关键取舍

### 3.1 Windows：启动时替换 vs 辅助进程

辅助进程方案（spawn helper 替换后退出）实现复杂且易被杀软拦截；
自用场景程序通常由守护/服务管理器拉起，**启动时替换**更简单可靠：
主进程退出 → 管理器拉起新进程 → Bootstrap 完成替换。代价是“更新
需要一次重启”，对服务类程序可接受。

### 3.2 校验：SHA256 必需 + Ed25519 可选

SHA256 防损坏/防篡改（传输中），Ed25519 防伪造（发布方私钥）。
自用 HTTPS + 私库场景下 SHA256 足够；公网分发建议启用签名。
标准库 `crypto/ed25519` 零依赖。

### 3.3 清单签名对象：规范化字节

对 `Signature` 置空后的清单规范化 JSON 签名：字段顺序与
map 排序由 `encoding/json` 保证，签名与校验均可复现，
实现简单且无歧义。

### 3.4 版本比较：自研轻量 semver

只实现 semver 2.0 核心（主/次/补丁/预发布/构建），不引入第三方
semver 库；非法版本明确报错。

### 3.5 全量下载 vs 差分

自用产物通常 10-100 MiB，全量下载实现简单、错误面小；差分更新
需要构建期生成补丁，复杂度不成比例。接口预留（Asset 可扩展）。

### 3.6 HTTP/3 承载升级

webx 底座已支持 HTTP/3（quic-go），httpx 提供协议切换；
自用升级链路统一走 HTTP/3：

- 单端口承载清单与资产，降低运维面；
- UDP 传输对弱网更友好（0-RTT/多路复用）；
- 与 webx 服务端天然同栈，示例即真实闭环。

## 4. 与既有底座的分工

| 底座 | 分工 |
| --- | --- |
| errx | 全部错误语义与错误码 |
| logx | 检查/下载/校验/替换结构化日志 |
| confx | Config 结构体直接加载 |
| httpx | 可选 HTTP 客户端（默认标准库） |
| jobx | 定时检查更新 |
| webx | 管理 API 触发更新 + 优雅重启 |
| authx | 更新 API 鉴权（业务组合） |
